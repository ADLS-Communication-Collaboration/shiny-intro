Basic Reactivity

The key idea of reactive programming is to specify a graph of dependencies so that when an input changes, all related outputs are automatically updated.

Wickham (2019) in Mastering Shiny
Why does this matter? Without reactivity, the entire R script would re-run every time anything changes in the app
aus Wickham (2019), Mastering Shiny

This makes the flow of an app considerably simpler, but it takes a while to get your head around how it all fits together.

Futher reading:

  • mastering-shiny.org/basic-reactivity.html
  • mastering-shiny.org/reactivity-intro.html
  • Highlighted: "Reactive Sources" — the input$* values created by UI widgets
  • Whenever a user interacts with a widget, its input value changes
  • Shiny automatically detects which outputs depend on that input and re-runs only those

Reactive Outputs 

						library(shiny)

						ui <- plotOutput("plot")

						server <- function(input, output, session){
							output$plot <- renderPlot(plot(rnorm(100)))
						}


						shinyApp(ui, server)
Reactive outputs always come in pairs: render*() to generate the output on the server, *Output() to display it in the UI.

  • See shiny.posit.co/r/articles/start/cheatsheet/
  • More output types are available at htmlwidgets.org
  • Reactive outputs always come in pairs: render*() to generate the output on the server, *Output() to display it in the UI.
  • The respective packages usually provide the functions needed to integrate their outputs into Shiny
  • Highlight 1: Reactive Sources — input$* values, set by UI widgets
  • Highlight 2: Reactive Conductors — reactive(), reactiveVal(): intermediate computations that cache their result and only re-run when their dependencies change
  • Highlight 3: Reactive Endpoints — output$* and observe(): consume reactive values and produce side effects (rendered output, file writes, etc.)
  • Data flows one direction: Sources → Conductors → Endpoints
